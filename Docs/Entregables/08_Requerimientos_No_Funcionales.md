# Tabla de Requerimientos No Funcionales
## Robot SCARA — Sistema de Simulación y Control

| ID | Categoría | Requerimiento | Métrica / Criterio | Fuente en código |
|---|---|---|---|---|
| **RNF-01** | **Rendimiento — Latencia** | La latencia de ida y vuelta (RTT) entre Unity y el ESP32 no debe exceder 50 ms en canal USB y 100 ms en Bluetooth en condiciones normales de operación. | RTT USB ≤ 50 ms · RTT BT ≤ 100 ms · RTT TCP ≤ 30 ms (localhost) | `RobotConfig.ReadTimeout = 500` (timeout máximo); ping/PONG cada 4s |
| **RNF-02** | **Rendimiento — Actualización** | La interfaz gráfica debe correr a mínimo 30 FPS y el modelo 3D debe interpolarse fluidamente usando Lerp en cada frame. No deben producirse bloqueos del hilo principal. | ≥ 30 FPS en hardware de referencia · Lerp en `RobotController.Update()` | `RobotController.LerpModel()` en `Update()`; threads separados para serial/BT/TCP |
| **RNF-03** | **Usabilidad — Resolución** | La interfaz debe estar diseñada para una resolución fija de 1920×1080 px en modo ventana. El layout debe ser generado proceduralmente sin depender de prefabs de escena. | Resolución fija 1920×1080 · `Screen.SetResolution()` al iniciar | `SplashScreen.Start()`: `Screen.SetResolution(1920, 1080, Windowed)` |
| **RNF-04** | **Fiabilidad — Thread Safety** | Las comunicaciones seriales, BT y TCP deben correr en hilos secundarios. Todos los mensajes deben pasar por colas thread-safe (`Queue<string>` + `lock`) antes de ser procesados en el hilo principal. | Cero `ThreadAbortException` · Shutdown limpio con `Join(500)` | `SerialManager._lock`, `BluetoothManager._lock`, `PythonSocketServer._lock` |
| **RNF-05** | **Compatibilidad** | El sistema Unity debe correr en Windows 10/11 (64-bit). El ESP32 debe usar el Arduino esp32 board package v2.0+. Python debe ser compatible con Python 3.8+. | Build target: Windows x86_64 · esp32 ≥ 2.0 · Python ≥ 3.8 | Dependencias: `System.IO.Ports` (Windows), `BluetoothSerial.h` (esp32) |
| **RNF-06** | **Mantenibilidad — Arquitectura** | El código C# debe estar organizado en namespaces (`ScaraRobot.Core`, `ScaraRobot.Communication`, `ScaraRobot.UI`, `ScaraRobot.Editor`) con una interface común `ICommunicationManager` para los canales seriales. | Cero clases sin namespace · Cero números mágicos sueltos · Todas las constantes en `RobotConfig` | Namespaces aplicados en todos los 22 scripts; `ICommunicationManager.cs` |
| **RNF-07** | **Seguridad — Emergencia** | El sistema debe disponer de un botón EMERGENCY STOP visible en todo momento que detenga el movimiento del modelo 3D y envíe el comando `STOP` al ESP32. El flag `emergencyStop` en `RobotState` debe bloquear `LerpModel()`. | Botón STOP siempre visible en TopBar · `state.emergencyStop = true` bloquea `Update()` | `RobotController.Update()`: `if (state.emergencyStop) return;` |
| **RNF-08** | **Escalabilidad** | Deben poder agregarse nuevos entornos (E6, E7...) sin modificar el núcleo del sistema. Los paneles de contenido por tab deben ser intercambiables mediante `UILayoutBuilder`. | Agregar nuevo entorno = agregar método `BuildEXPanel()` en `UILayoutBuilder` sin tocar `RobotController` | Patrón tab en `UILayoutBuilder` · Separación Core/Communication/UI mediante namespaces y `.asmdef` |
